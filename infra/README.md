## Environments

| Env | GCP project (placeholder) | Profile | Deploys from |
|---|---|---|---|
| dev | `noname-crm-dev` | `development` (scale to zero, small DB) | push to `develop` → `cloudbuild/build-and-deploy.yaml` with `_ENV=dev` |
| staging | `noname-crm-staging` | `production` | push to `main` → `cloudbuild/build-and-deploy.yaml` with `_ENV=staging` |
| prod | `noname-crm-prod` | `production` | manual → `cloudbuild/promote.yaml` with `_SHA=<staging sha>` |

Staging and prod are identical: both use the `production` profile (same Cloud Run sizing, HA Cloud SQL,
backups + PITR, deletion protection). Prod never rebuilds; it promotes the exact images staging ran.
Use staging for live online tests, then promote.

Region: `southamerica-west1` for everything.

## What the `platform` module creates (per environment)

- Artifact Registry `apps` repo (crm, pos, migrator images) **with cleanup policies**.
- Cloud SQL for PostgreSQL 17 (`noname_crm` database), reachable only through the Cloud SQL connector.
- Secret Manager secret `noname-<env>-database-url`.
- Cloud Run services `noname-<env>-crm` and `noname-<env>-pos` (public; auth is in-app), plus the
  Cloud Run job `noname-<env>-migrate` that runs `prisma migrate deploy`.
- Service accounts with least privilege: one per app, one for the migrator, one deployer for Cloud Build.
- Log retention (7 days dev, 30 days staging/prod).

## No stale images

Earlier projects accumulated an image per release until storage filled up. Here, every layer cleans up:

1. **Artifact Registry cleanup policies** (`modules/platform/artifact_registry.tf`): keep the 5 newest
   versions per image, delete untagged digests after 1 day, delete anything older than 14 days that
   isn't among the 5 newest. Running revisions are pinned by digest, so this never breaks them.
2. **SHA-only tags**: no moving `latest` tag, so old images don't linger as untagged leftovers.
3. **Revision pruning**: each pipeline ends with `scripts/prune-cloud-run-revisions.sh` (keeps the serving
   revision + 3 newest) and `scripts/prune-job-executions.sh`.
4. **No VMs**: everything runs on Cloud Run / Cloud Run jobs, so no host disk fills up with pulled images.
5. **Ephemeral builds**: Cloud Build workers are discarded after each build; nothing is cached on a machine.

## First-time setup (when you're ready)

```bash
# per environment (example: staging)
gcloud projects create noname-crm-staging           # or use an existing project; link billing
gcloud storage buckets create gs://noname-crm-staging-tfstate \
  --project noname-crm-staging --location southamerica-west1 \
  --uniform-bucket-level-access --public-access-prevention
gcloud storage buckets update gs://noname-crm-staging-tfstate --versioning

cd infra/terraform/environments/staging
# set the real project id in terraform.tfvars
terraform init
terraform plan
terraform apply
```

Then create the Cloud Build triggers (they need your GitHub connection) using the
`deployer_service_account` output as the trigger's service account. For prod promotion, grant the prod
deployer `roles/artifactregistry.reader` on the staging `apps` repository.

The database password is generated by Terraform and also stored in state, so keep the state buckets
private (as created above).
